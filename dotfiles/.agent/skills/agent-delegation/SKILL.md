# エージェントへの委譲

共通規約の委譲・レビュー条件に該当するときに読みます。この skill 自体は委譲の権限や対象範囲を広げません。

## 使いどころ

- subagent は、独立した調査、レビュー、検証、ログ分析、文書確認、または明確に分離できる作成・実装に使ってください。使うと決めた subagent への投入トークンは、共通規約の冒頭方針どおり惜しまないでください。
- 迷った場合は、書き込みや意思決定はメインの agent に集約し、subagent は情報収集、別視点のレビュー、検証、助言で補助する形を優先してください。
- 複数の問題を委譲する場合は、独立した問題領域ごとに分けてください。関連する失敗や共通原因が疑われるものは、無理に並列化しないでください。
- 複数の失敗に共通原因が疑われる場合は、共通原因の probe を main agent または1体で先に実施し、結果を確認してから後続を分岐してください。

## レビュー・助言の依頼

- 調査・レビュー・検証系の subagent は、原則として read-only または最小権限で使い、生ログではなく根拠付きの要約を返させてください。
- レビューや検証を任せる場合は、writer 側の検討過程を必要以上に渡さず、変更差分または成果物、目的、検証結果、気になっているリスクを渡してください。依頼文には、read-only の徹底、重大度順(重大・中・軽微)+ file:line での指摘、問題がなければ「重大な問題なし」と明記すること、を含めてください。必要に応じて白紙に近い context で開始させ、writer の説明をなぞらせるのではなく、差分、仕様、テスト結果そのものから問題を探させてください。依頼文に skill 名を列挙せず、出力形式は依頼文で指定してください(reviewer が skill を連鎖して読むのを避けるため)。
- reviewer の指摘はそのまま適用せず、メインの agent が全体方針、ユーザー指示、既存判断と照合して採否と追加検証を決めてください。
- 指摘の重大度と対応要否を分け、メインの agent が「今回必須・別件・対応不要」に分類してください。今回必須には、問題が成立する入力・状態と、現在の要件・正しさ・安全性への具体的な影響を求めてください。将来の拡張案は別件、誤認・重複・新しい根拠のない合意済み判断の蒸し返しは対応不要とし、理由を残してください。
- レビュー対象の版・commit・未commit差分を特定し、対象が変わったら以前の結果をそのまま流用しないでください。再レビューには前回の未解決指摘と修正差分、影響する呼び出し元・契約を渡し、修正の成立と回帰を確認してください。仕様・共有境界が変わる場合は関連する全体も確認してください。
- レビューは今回必須の指摘が解消し、受け入れ条件に対応する必要な検証が通ったら終了してください。反復しても進展しない場合は前提・設計を見直し、判断が必要なら未解決事項を示してください。回数上限だけを理由に必須の指摘を別件へ格下げしないでください。
- 難しい設計判断、原因が広い不具合、merge conflict、セキュリティやデータ損失の懸念、視覚確認やテスト戦略など、特定能力の補助が有効な場面では、広めの質問で助言を求めて構いません。助言側が前提不足を指摘した場合は、推測で埋めず、追加調査してから統合してください。

## 委譲の手順

- メインの agent が方針、クリティカルパス、並列化できる副タスクを決める。
- 出力依存がなく、同じファイルや共有状態を変更しない独立した副タスクが2件以上ある場合は、最初の待機前に同じ wave の agent をまとめて起動する。2件なら2体、3〜5件なら同数を1 wave、6件以上なら3〜5体ずつの複数 wave に分ける。件数を合わせるために仕事を水増しせず、全対象の欠落と重複を確認する。
- 出力依存がある直列工程では、前段の結果を待ち、メインの agent が根拠と採否を確認してから後段を起動・実行する。
- 依頼文に目的、対象範囲、制約、完了条件、期待する返答形式を含める。
- 作成や実装を任せる場合は、担当ファイル、成果物、責務を分離し、他の subagent や並行作業による変更を巻き戻さないよう明示する。
- 複数の作成・実装 subagent を使う場合は、共有すべき決定、前提、進捗、発見事項をメインの agent が明示的に橋渡しする。subagent 同士が暗黙に同じ context や状態を共有している前提で進めない。
- subagent の実行中、メインの agent は重複しない作業を進め、必要なときだけ十分な長さで待つ。短い個別 polling を繰り返さない。
- subagent の完了を待つときは、利用中の実行環境が提供する待機手段を使う。待機時間を指定できる場合は、完了までの推定残り時間の2倍を目安に、許容される範囲内で設定する。見積もれない場合は、その環境の既定値を使う。完了通知や待機の中断はその環境の仕様に従い、短い確認のために待機を繰り返さない。タイムアウト後は完了見込みを更新して待つ。並行作業の有無は待機に入るかどうかの判断基準であり、待機時間の決め方には影響させない。
- 各 wave の結果は収集と検証だけを行い、失敗した枝があれば最終統合前にその枝だけを再実行して待つ。再実行する枝が3件未満でも仕事を水増しせず、成功済みの枝はやり直さない。予定した全 wave と再実行が完了してから、全体を一度だけ最終統合する。
- 大きな作業は、無構造に多数の agent を走らせず、メインの agent がタスクを分解し、各 subagent の成果を回収して判断を統合する map-reduce 型で進める。
- custom subagent は、呼び出し条件、責務、許可・禁止ツール、権限、外部連携の範囲を明確にし、単一責務で再利用できるものだけを定義する。
