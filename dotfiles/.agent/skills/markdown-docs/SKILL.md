# Markdown Docs

Markdown 文書そのものの構成、記法、リンク、表を作成、編集、レビューする。日本語文の自然さは `natural-japanese` の担当で、本 skill では扱わない。project に同名の skill があればそちらだけを読む。

## 着手前の判定

- 依頼が数値・出典・事実の照合、コード変更、スライド・PDF・LaTeX なら本 skill は不要。読んだ時点で対象外と分かったら、以下の手順を適用せず本来の作業へ戻る。
- 「レビュー」「校閲」だけの依頼はファイルを変更せず指摘を返す。修正も依頼されていれば反映まで進める。
- 対象読者、言語、文体、変更範囲は既存文書と同種の文書から読み取り、決められない場合だけ短く確認する。

## 共通ルール

構成

- H1 は 1 つ。階層を飛ばさない(H2 の下に H4 を置かない)。同じ階層の見出しは並列な形にし、内容が分かる語で書く。
- 同種の既存文書(他の README、docs/ 配下)があれば、その節構成と順序に合わせる。
- 表は比較や一覧に利点があるときだけ使い、単純な列挙は箇条書きにする。

記法

- コードフェンスには言語を付ける。コマンド、ファイルパス、API 名、設定キー、エラー文は backtick で囲み、言い換えない。
- リンクテキストは具体的にする(「こちら」を避ける)。画像には内容を表す alt を付け、装飾画像は空の alt にする。
- 用語、文体(です/ます・である)、日付形式、箇条書きの記号を文書全体で統一する。

リンクと表示

- 相対リンク、画像パス、見出しアンカーは実在を確認する(`ls` と `grep -n '^#' <file>` で足りる)。
- Notion や Slack へ貼る文書は、承認済みの貼り付け後に `*`、`•`、強調が落ちないか確認する。未承認の外部送信はせず、ローカルで確認できた範囲と残る確認を報告する。

出力の長さ

- 校正・編集の出力は原文と同程度の長さに留め、依頼にない前置き、要約、追加説明を足さない。文章系 skill で「もっと短く」と直された例は、依頼範囲を超えて書き足したときに起きている。

## ワークフローごとの違い

作成

- 入力資料と既存テンプレートから文書の種類、読者、必須節、言語、構成を決め、完成稿まで進める。結果が大きく変わる不明点がある場合だけ質問し、構成の合意が明示された依頼ではその段階で止める。

編集

- 既存の文体、見出し階層、リンク形式、コードブロック言語に合わせる。依頼範囲外の段落は整形も含めて触らない。
- 編集後に差分を読み、意図しない変更が混ざっていないか確認する。

レビュー

- 対象範囲の構成、過不足、読者適合を確認する。文書全体のレビューでは `references/review-checklist.md` を開き、局所編集では必要な観点だけ使う。
- 指摘は重要度順(高・中・低)に、位置(見出しまたは行)と改善案を付けて返す。問題がなければ「重大な問題なし」と明記する。

## エンジニアリング文書の Why

README、設計メモ、リリースノート、ADR、runbook では、何をしたかに加えて、理由、捨てた代替案、影響範囲、未検証事項を残す。PR / CL description のテンプレートが要るときだけ `eng-practices` を読む。

## 最終報告に含めるもの

- 変更または確認したファイル
- 主な編集内容(構成変更、記法修正、リンク修正の別)
- リンク・アンカー確認の有無と、貼り付け先での表示確認の有無
- 未確認事項(外部リンクの生存、数値・出典の正しさなど)
