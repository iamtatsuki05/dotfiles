# Auto Debugger

CIの定義・実行基盤の失敗は `ci-cd` に任せる。エラーの原因を観測で絞り、依頼が修正を含む場合は最小変更と検証まで進める。説明・調査だけの依頼ではコードを変更しない。

## 原因を絞る

- エラー、入力、再現操作、失敗行と直前の変更を確認する。まず関係するコードとテストを読み、根拠に応じて調査範囲を広げる。
- 最小の再現方法または観測手段を確保する。既存の失敗テスト、ログ、デバッガで仮説を区別できれば、それを使う。
- 中間値が必要なときだけprintデバッグや独立した検証スクリプトを使う。補助ファイルはOSの一時ディレクトリか既存のテスト用scratch領域に置く。作業後は今回作成した補助ファイルだけを片付け、削除できなければ対象と理由を報告する。
- 同じ仮説で進展しない場合は、観測事実と推測を分け、別の原因や逆向きの検証を試す。ユーザーへの質問は、手元で取得できない必要情報が残る場合に限る。
- `.env` や認証情報を参照・出力しない。設定依存の問題では秘密を含まない設定名、存在確認、伏せた診断結果で検証する。

## 修正と完了

- 修正が依頼されていれば、原因を解消する最小変更を行う。言語固有の実装規約は該当スキルから必要なものを使う。
- 自動化に適した不具合には、修正前に失敗し修正後に成功する回帰テストを追加する。既存テストで十分なら重複を増やさない。
- 変更に合う検証とrepo指定の検査を実行する。外部サービスなどで実行できない検証は、代替の観測結果と未検証範囲を明示する。
- 調査で見つけた無関係な問題は報告に留める。修正後は原因、変更点、検証結果、残る不確実性を返す。

## 必要な場合に読む資料

- 再現が不安定な不具合・性能退行: `diagnosing-bugs`。切り替え時は再現手順と検証済み仮説を引き継ぎ、同じ調査や複数の手順を重ねない。
- よくある落とし穴を疑う場合: [エラーパターン別の調査メモ](references/error-patterns.md)。
- PR提出を依頼された場合: `git-github-flow` とrepoのPR規約。
