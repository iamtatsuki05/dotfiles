# 提出前チェックリスト

PR を出す直前、PR 説明を書くとき、レビュー指摘に返答するときに、上から順に当てはめる。

## 実装者向け(PR を出す直前)

- [ ] PR の目的は 1 文で言えるか(複数目的が混在していないか)。
- [ ] テストを同じ PR に入れたか。難しい場合は理由と代替検証を PR 説明に書いたか。
- [ ] 行数は 100 行前後 / 400 行以内か。超える場合、再分割を検討したか。
- [ ] 公開 API、保存データ、運用への影響を PR 説明に書いたか(破壊的変更があるなら明示)。
- [ ] コードコメントは Why を書いているか。What の重複コメントは消したか。
- [ ] build / lint / test / 型検査の結果を集めたか。未実行があれば理由をメモしたか。

## PR 説明を書く人向け

- [ ] タイトルは命令形・短く・具体的か(`Bug fix` / `Update` / `WIP` だけになっていないか)。
- [ ] Why を本文に書いたか(背景、動機、捨てた代替案)。
- [ ] What を要約として書いたか。
- [ ] ロールバック計画があるなら本文に書いたか。
- [ ] 未検証項目を未検証として明示したか。
- [ ] 関連 issue / 設計ドキュメント / 過去 PR / 再現手順をリンクしたか。

## レビュー指摘を受ける人向け

- [ ] 感情で反応していないか。
- [ ] まず「コード自体で直せないか」を検討したか(説明追加より構造改善)。
- [ ] 反論するときは事実(スタイルガイド、測定値、過去 incident)で根拠を示したか。
- [ ] 採用しないコメントには理由と代替対応(issue / TODO リンク)を返したか。
- [ ] 「後で直す」を口頭約束で済ませず、issue / TODO を切ったか。
- [ ] 全コメント対応後、再レビュー依頼を明示したか。
- [ ] force push 必須の repo なら、変更点を PR コメントで要約したか。
